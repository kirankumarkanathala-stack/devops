Authentication vs. authorization

Authentication asks “Are you in the system?”
Like showing your employee ID card at the front gate.
Authorization asks “Can you use this resource?”
Like having access to one project room or database.

Users & groups

Every user has exactly 1 primary group and 0 or more secondary groups.

/etc/passwd
Username, UID, primary GID, home path, default shell.
/etc/group
Group name, GID, member list.
Create a user
sudo useradd ramesh

Auto-creates a UID (≥ 1000), the home directory /home/ramesh, and a primary group named ramesh.

Set or change a password
sudo passwd ramesh

Prompts you to set the password.

Check user details
id ramesh

Shows UID, primary GID and secondary GIDs.

Create a group
sudo groupadd devops

Adds a record to /etc/group.

Change the primary group
sudo usermod -g devops ramesh

-g sets the single primary group.

Add a secondary group
sudo usermod -aG sre ramesh

-G names the secondary group. -a appends, so existing groups are not replaced.

Remove a user from a group
sudo gpasswd -d ramesh devops

-d deletes the user from the named group.

Permissions & ownership

Run ls -l to see a 10-character string. Read it in four parts.

-rwxr-xr--
Char 1: - file or d directory Chars 2–4: owner (u) Chars 5–7: group (g) Chars 8–10: others (o)

Try the octal calculator

r (4)w (2)x (1)
Owner (u)
Group (g)
Others (o)
000
---------
chmod 000 file.txt

Number values

7 = rwx6 = rw-5 = r-x4 = r--1 = --x0 = ---
751
Owner rwx, group r-x, others --x
440
Owner r--, group r--, others ---
Only the file owner or root can change permissions.

Commands

Add execute for the owner
chmod u+x file.txt
Add write for the group
chmod g+w file.txt
Remove everything from others
chmod o-rwx file.txt

Symbolic method: u, g, o with + (add) or - (remove).

Change the owner
sudo chown suresh file.txt
Change owner and group
sudo chown ramesh:devops file.txt
Change a whole directory
sudo chown -R suresh:sre /tmp/aws

-R is recursive: it covers every file and subdirectory.

Only root can change ownership. File owners cannot hand a file to someone else.

Sudo (admin rights)

Without permission, sudo fails with “ramesh is not in the sudoers file”. Two ways to fix it.

Option A: simple

Add to the wheel group

sudo usermod -aG wheel ramesh

Wheel members can run every admin command. The user must log out and back in for it to apply.

Option B: best practice

Use a file in /etc/sudoers.d/

Do not edit /etc/sudoers directly. Create /etc/sudoers.d/ramesh instead.

What to write in the file

Full access, no password
ramesh ALL=(ALL) NOPASSWD: ALL
Only specific commands
ramesh ALL=(ALL) NOPASSWD: /usr/sbin/useradd, /usr/sbin/usermod

Ramesh can run only those binaries with sudo. No root shell, no other commands.

  1. Lock down the filesudo chmod 440 /etc/sudoers.d/ramesh. If permissions are more open, Linux ignores the file and reports a bad permissions error.
  2. Check the syntaxsudo visudo -c checks all sudoers files for errors.

SSH login

Cloud Linux (like AWS EC2) blocks passwords by default and requires keys.

Turn on password login

  1. Open the configsudo vim /etc/ssh/sshd_config
  2. Edit line 65Change PasswordAuthentication no to PasswordAuthentication yes
  3. Test the syntaxsudo sshd -t prints nothing if all is clean.
  4. Restart SSHsudo systemctl restart sshd
  5. Log inssh ramesh@<IP_address>

Key-based login

  1. User makes a key pairPublic and private key, on their own machine.
  2. User sends the public keyThe private key never leaves their machine.
  3. Admin stores it/home/ramesh/.ssh/authorized_keys
  4. User connectsssh -i ramesh_private_key.pem ramesh@<IP_address>
  5. Server checks the matchIt finds ramesh, opens authorized_keys, and confirms the private key matches the stored public key. Match means access.

DevOps context

Why learn CLI user management?

Even with SSO, you use it when writing Dockerfiles, running apps as non-root, securing containers, and setting cloud IAM rules.

Never edit production by hand

Keep config files in Git. Review them with pull requests. Deploy through CI/CD.

Moving into DevOps

From Java development or manual testing, treat your background as an asset. Build your resume around hands-on projects, not generic templates.
